# Security Policy

## Supported Versions

NeuralMint is pre-1.0. Security fixes target the `main` branch and the most
recent tagged release.

| Version | Supported |
| ------- | --------- |
| 0.1.x   | Yes       |
| < 0.1   | No        |

## Reporting a Vulnerability

Do not open public issues for security vulnerabilities.

Report privately through GitHub Security Advisories:
<https://github.com/NeuralMintdev/neuralmint/security/advisories/new>

Please include:

- A description of the issue and its impact.
- Steps to reproduce, ideally against localnet.
- Affected component and commit hash.

### Response Targets

- Acknowledgement within 48 hours.
- Initial assessment within 7 days.
- Fix timeline communicated based on severity.

## Threat Model

The program is designed around a small set of invariants:

- The vault authority is a PDA with no external private key. Funds can only move
  through `wrap` and `unwrap`.
- `unwrap` requires proof of ownership of exactly one unit of the gating NFT.
- There are no admin or upgrade-authority instructions in the program logic.

Areas that warrant particular scrutiny in review:

- Account substitution on `unwrap` (mint, holder account, vault ATA).
- Arithmetic on `locked_amount` (guarded by checked operations).
- Token-2022 extension interactions (transfer fees, hooks) on the wrapped mint.

## Operational Guidance

- Never commit keypairs. The localnet keypair is generated by `scripts/setup.sh`
  and lives outside the repository.
- Pin toolchain versions (`Anchor.toml`, CI) to reproduce builds.
- Treat the deployed program id as immutable; deriving vaults from a different id
  yields different addresses.
